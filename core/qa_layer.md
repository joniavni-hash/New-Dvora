# QA Layer
<!-- Status: Active -->
<!-- Purpose: Quality checks before any external action -->

## תפקיד
בדיקת איכות לכל תוצר לפני שיוצא. אם check אחד נכשל — הפעולה נעצרת.

## בדיקות

### 1. Factual Fit
- האם העובדות נכונות?
- האם יש טענה שלא מגובה?
- האם יש סתירה עם מידע ידוע?
- **האם המקורות אמיתיים?** (URLs שנשלפו בפועל vs fabricated)
- **האם ה-agent השתמש בכלים כשהיה צריך?** (research בלי web_search = fail)

### 2. Style Fit
- האם הטון מתאים ליעד? (קבוצה, DM, מייל פורמלי...)
- האם האורך סביר?
- האם השפה נכונה? (עברית/אנגלית)

### 3. Policy Fit
- האם עומד ב-policies שנטענו?
- האם ה-role מאפשר את הפעולה?
- האם ApprovalGate מאשר?

### 4. Risk Check
- סיכון פרטיות: האם חושפים מידע של יוני?
- סיכון מבוכה: האם זה יכול להביך?
- סיכון conflict: האם זה מתערב בויכוח?
- סיכון דיוק: האם אנחנו בטוחים מספיק?

### 5. Missing Context
- האם חסר מידע קריטי שישנה את התשובה?
- האם ה-agent ניחש במקום לדעת?

### 6. Wrong Action
- האם ה-agent השתמש בכלי לא נכון?
- האם התשובה עונה על מה שנשאל?
- האם ה-agent חרג מהתפקיד שלו?

## זרימה
```
1. Agent מחזיר output
2. דבורה מריצה את 6 הבדיקות
3. הכל עובר → ממשיך ל-ApprovalGate
4. בדיקה נכשלת → עוצרים, דבורה מחליטה:
   - לתקן ולשלוח
   - לבקש מה-agent לנסות שוב
   - לבטל
```

## Self-QA של Agent
כל agent גם מריץ QA עצמי (qaResult ב-output). אבל **דבורה תמיד בודקת בעצמה** — לא סומכת רק על ה-agent.

## דוגמאות כשל
| בדיקה | דוגמה | פעולה |
|--------|--------|-------|
| Factual | Agent אמר שפגישה ביום שני כשהיא ביום שלישי | תיקון |
| Style | תשובה פורמלית בקבוצת חברים | עריכה |
| Policy | תשובה בקבוצה observer | ביטול |
| Risk | חשיפת כתובת יוני | ביטול |
| Missing | תשובה על טיסות בלי לבדוק מחירים | חקירה נוספת |
| Wrong Action | Agent שלח במקום להחזיר draft | ביטול + trace + תיקון prompt |
