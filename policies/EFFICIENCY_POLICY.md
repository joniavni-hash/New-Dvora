## מטרה
לצמצם tool calls מיותרים בלי לפגוע באיכות. כל tool call עולה זמן — צריך להצדיק אותו.

---

## Tool Call Gate

לפני כל tool call, שלוש שאלות:

### 1. האם המידע כבר אצלי?
- בקבצי workspace שנטענו אוטומטית (AGENTS, SOUL, IDENTITY, HEARTBEAT, TOOLS, USER, MEMORY)
- בשיחה הנוכחית
- בתוצאות של tool call קודם באותו turn

אם כן → לא לקרוא.

### 2. האם התוצאה תשנה את התגובה?
- אם אני כבר יודעת מה לענות, ו-tool call רק "יוודא" → לא לקרוא.
- אם יש ספק אמיתי שמשפיע על התשובה → כן לקרוא.

### 3. האם אפשר לאגד?
- כמה reads עצמאיים → במקביל.
- כמה exec עצמאיים → פקודה אחת עם `&&`.
- read + exec שלא תלויים → במקביל.

## חמישה כללים

### 1. לא לקרוא מה שכבר טעון
קבצי workspace context נטענים אוטומטית. לא לקרוא אותם שוב.

### 2. לא לקרוא לפני כתיבה כשהתוכן ידוע
אם יוני נתן טקסט מדויק ליצירת קובץ → `write` ישירות.
`read` לפני `edit` רק כשצריך מיקום מדויק או בדיקת תוכן קיים.

### 3. לא לחפש ב-memory כשהתשובה בהקשר
`memory_search` רק כשבאמת חסר מידע שלא נמצא בשיחה או בקבצים טעונים.

### 4. תשובות טקסט לא דורשות tools
תשובה, אישור, הסבר, דעה → פשוט לענות. בלי read, בלי search.

### 5. כלל 3 הניסיונות
אם tool call או גישה נכשלו 3 פעמים:
→ לא לנסות עוד.
→ להחזיר כיוון (RESPONSE_STRATEGY: 🔄).
→ להציע חלופה או לשאול את יוני.

### 6. אל תרימי ידיים — כלל מוחלט
לפני כל תשובה שלילית ("אין לי", "לא זמין", "לא אפשרי"):
→ רשימת בדיקה מחייבת:
  1. scripts/ — האם יש סקריפט רלוונטי?
  2. memory/ — האם יש מידע שנשמר?
  3. integrations/ — האם יש אינטגרציה מתועדת?
  4. HEARTBEAT.md / context טעון — האם יש רמז שהיכולת קיימת?
  5. browser — האם אפשר לעשות את זה דרך דפדפן?
  6. exec — האם אפשר להריץ פקודה חלופית?
  7. API חלופי — האם יש דרך אחרת להגיע לאותה תוצאה?
→ רק אחרי שמיצית לפחות 3 אפשרויות — מותר להגיד "לא יכולה".
→ זו הכשלה מספר 1 של המערכת. שלוש פעמים ביום אחד (20.3.2026).

## דפוסים שכיחים לחיסכון

| מצב | במקום | לעשות |
|-----|-------|-------|
| יוני נתן טקסט ליצירת קובץ | read → write | write ישירות |
| שאלה על משהו שדיברנו עליו | memory_search | לענות מהשיחה |
| 3 פקודות exec עצמאיות | 3 tool calls | exec אחד עם && |
| קובץ workspace context | read | כבר טעון, לענות |
| בדיקת סטטוס + פעולה | exec, exec | exec אחד |

## מתי כן להשתמש ב-tools
- מידע שלא בהקשר ולא בשיחה
- ביצוע פעולה (כתיבה, שליחה, הרצה)
- ספק אמיתי לגבי מצב נוכחי
- דיוק קריטי שעדיף על מהירות

## כלל זהב
tool call צריך להצדיק את עצמו.
אם הוא לא משפר את התשובה → לא לקרוא.
אם יש ספק אמיתי → עדיף tool call מיותר מתשובה לא מדויקת.
