# FALLBACK_POLICY.md — מדיניות נסיגה בכשלים

## עיקרון
כשמשהו נכשל — לא לנסות שוב בלי סוף, לא להתעלם, ולא לאלתר בשקט. יש סדר ברור.

## כשל ב-API חיצוני (Graph, Google, Control4 וכו')

```
ניסיון 1 → נכשל → חכי 3 שניות → ניסיון 2
ניסיון 2 → נכשל → דווחי ליוני: "[שירות] לא מגיב. אנסה שוב מאוחר יותר או שתגיד לי לוותר."
```

- לא יותר מ-2 ניסיונות אוטומטיים
- לא לנסות שוב בלי שיוני ביקש או שעבר heartbeat

## כשל ב-token / אימות

```
Token expired / 401 / 403 →
1. נסי לחדש token (refresh) אם יש refresh flow
2. אם גם זה נכשל → דווחי ליוני עם פירוט מדויק של השגיאה
3. לא לנסות credentials ישנים שוב
4. לא להציע ערוצים אחרים כתחליף אוטומטי — כל ערוץ הוא נפרד
```

### אבחון שגיאות אימות
- `invalid_client` → Secret פג תוקף ב-Azure. להגיד ליוני ליצור חדש.
- `missing_credentials` → Secret לא מוגדר. לבדוק /home/ubuntu/.openclaw/.env.
- `401/403` → הרשאות חסרות. לבדוק את ההגדרות ב-Azure Portal.
- Timeout → בעיית רשת. לנסות שוב מאוחר יותר.

## כשל בכלי (browser, exec, gog)

```
כלי לא עובד →
1. נסי גישה חלופית אם יש (למשל: browser נפל → נסי web_fetch)
2. אם אין חלופה → דווחי ליוני: "[כלי] לא זמין כרגע."
3. לא להמציא פתרונות שלא נבדקו
```

## כשל בשליחת הודעה

```
הודעה לא נשלחה →
1. ניסיון נוסף אחד
2. אם עדיין נכשל → שמרי את ההודעה ודווחי ליוני בהזדמנות הראשונה
```

## כשל בפעולה חיצונית (שליחת מייל, יצירת אירוע)

```
נכשל →
1. לא לנסות שוב אוטומטית — פעולות חיצוניות הן חד-כיווניות
2. דווחי ליוני מיד: "ניסיתי ל-[פעולה] ונכשלתי. סיבה: [X]."
3. שמרי את הטיוטה/נתונים כדי שלא יאבדו
```

## כלל על state/health_check.json
- **לעולם לא להסתמך על תוצאות health check ישנות כדי להחליט שמערכת לא עובדת**
- אם health_check.json מראה כשל — עדיין לנסות את ה-API בפועל
- health check ישן (מעל 24 שעות) לא רלוונטי — secrets יכולים להתחדש, שירותים יכולים לחזור

## כלל עליון
- **לעולם לא להתעלם מכשל בשקט**
- **לעולם לא ללופ** — 2 ניסיונות מקסימום
- **לעולם לא לאלתר** פעולה חיצונית אחרת כ-fallback בלי אישור
- **תמיד לדווח שגיאה מדויקת** — לא "אין גישה" אלא מה בדיוק נכשל ומה צריך לעשות
- **תמיד לשמור** את מה שהיה צריך לקרות, למקרה שיוני ירצה לנסות שוב
